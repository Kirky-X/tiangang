# SAST 误报模式知识库（False Positive Patterns）

triage（`generate_report.py --triage` 的三态裁决）与人工复核前，先核对这份清单——把「我觉得是误报」变成「命中了哪个模式、证据是哪一行」。规则命中只是模式匹配的产物，模式 ≠ 漏洞；这份清单是裁决前必须过的模式核对层。

核对纪律（两条硬规则）：

1. **判 `false_positive` 前必须指认命中的模式类别，并引用证明它的源码行号。** 指认不出类别、拿不出证据行，就不是误报——写 `needs_validation` 并点名缺失的事实。
2. **判 `true_positive` 前先做文末的魔鬼代言人复核**：构造最强的"这是误报"论证，论证失败才放行，并在 reasoning 里写明排除了哪个模式类别、为什么。

## 误报模式清单

每条给识别特征（什么样子会像命中）与判定方法（怎么证实/证伪）。

### 1. 测试与夹具代码

- **识别特征**：路径在 `tests/`、`test_*`、`*_test.py`、`spec/`、`fixtures/`、`mock*` 下；文件只被测试加载器引用。
- **判定方法**：测试代码默认不在生产攻击面，绝大多数命中可判误报。两个例外是**真问题**：(a) gitleaks/trufflehog 命中测试文件里的凭证——测试里硬编码的真实凭证照样入库、照样泄露，判 TP 并轮换；(b) 测试辅助脚本被构建/部署脚本引用（`scripts/` 被打包、Makefile 目标调用），测试代码会随制品进生产。判定动作：确认文件只被测试消费，再下 FP。

### 2. 防御式编程被当成漏洞点

- **识别特征**：命中的"危险操作"本身是校验代码——`assert len(x) < N` 后的分支、`if not valid: raise` 的异常路径、显式的边界检查语句。
- **判定方法**：规则无法区分"做危险事的代码"和"防危险事的代码"。沿数据流向上找：sink 收到的输入是否已被前面的校验完整约束。校验完整覆盖输入域 → FP；只覆盖部分（比如只查了 `None` 没查长度）→ 仍是 TP。判定证据是具体那行校验，不是"看起来有检查"。

### 3. 条件逻辑造成的不可达路径

- **识别特征**：漏洞分支需要某个输入条件成立，但上游条件判断使该条件**数学上不可能**成立——例如先校验 `length >= 12`，后面才取 `buffer[length - 4]`，下溢条件被前置判断排除。
- **判定方法**：列出从入口到 sink 的全部条件组合，逐一证明无一能满足漏洞前提。能列出完整组合并证伪 → FP；有一条路径说不清 → 不是 FP，走 needs_validation。孤立地看 sink 所在片段永远判不了这一类——必须看完整条件链。

### 4. 框架/语言内建防护覆盖的 sink

- **识别特征**：sink 是 ORM 参数化调用、模板引擎自动转义输出、React JSX 默认转义、带占位符的 database driver API。
- **判定方法**：确认代码走的**确实是**安全 API 形态：`cursor.execute(sql, params)` 是参数化，`cursor.execute(f"...{x}...")` 不是；模板变量输出 `{{ x }}` 是转义的，`render_template_string(动态串)` 不是。框架只保护它保护的入口——绕过惯用法（raw 查询、`__html`、`dangerouslySetInnerHTML`）不受保护。找不到框架防护的实际调用点就判 FP 是猜测，不是裁决。

### 5. 已消毒的数据流

- **识别特征**：source 与 sink 之间存在 `sanitize`/`escape`/`quote`/`allowlist`/白名单校验调用。
- **判定方法**：两点必须同时成立才算消毒有效：(a) 消毒函数作用在**这条流上**（taint 在此断开——作用在别的变量上不算）；(b) 消毒手段对**这个 sink**完备——`shlex.quote` 对 shell 有效、对 SQL 无效；`int()` 转换有效但 `str(int(x))` 之后再拼接要重看；HTML 转义对属性上下文未必够。缺任何一点，命中仍是 TP。

### 6. 文档、示例与配置样例

- **识别特征**：`README`、`docs/`、`examples/`、`*.example`、`*.sample` 后缀，注释块里的示例代码，脚手架生成的演示文件。
- **判定方法**：确认文件不参与构建、不被部署、不被 `import`。纯文档 → FP。例外：会被复制部署的样例配置（`config.example.yaml` 被 CI 当模板填充真实值）是真问题；示例代码被用户原样拷走率高（如 SDK 示例目录）时标注 TP 候选并降严重度，而不是直接 FP。

### 7. 攻击者不可控的输入源

- **识别特征**：sink 收到的数据来自编译期常量、受信内部配置、服务端硬编码枚举、安装期由可信组件写入的内部存储。
- **判定方法**：从 sink 反向追溯 source 到头。source 是外部输入（请求参数、环境变量外部可影响、用户上传、外部服务响应）→ 保持 TP 候选；source 全程在信任边界内 → FP。注意"内部存储"不等于"攻击者不可控"——如果内部值最初源自外部输入（如从请求写进 DB 再读出），污染仍在流里。

### 8. 整数边界数学上不可行

- **识别特征**：规则报整型下溢/上溢/越界，但校验与后续运算存在明确的数学关系——`packet_size >= MIN` 且 `MIN >= header_size`，则 `packet_size - header_size` 不可能为负。
- **判定方法**：写出代数证明：IF 校验成立 THEN 边界保证成立。证明成立 → FP（证据是这组不等式本身）；写不出证明 → 保持 TP 候选。这一类和模式 3 常一起出现：不可达是路径层面的，这里算的是数值层面的。

### 9. 无并发可能的竞态申报

- **识别特征**：规则报 TOCTOU/race，但 check 与 use 在同一函数内同步完成，或代码只运行在单线程初始化路径、持锁区间、事件循环单线程模型里。
- **判定方法**：竞态成立需要证明**并发到达确实可能**：存在多个执行入口、检查值可在 check 与 use 之间被外部改变。证明不了并发可能 → FP。能并发但窗口极窄不是 FP——窗口宽窄影响的是可利用性评级，不是存在性。

### 10. 纵深防御层失效被拔高成漏洞

- **识别特征**：命中点是第二道及以后的防线——内层再校验缺失、清理逻辑（token 清理、缓存失效、日志脱敏）有缺陷，而主控制（鉴权、参数化、单次使用设计）完好。
- **判定方法**：问一个问题：**主控制失效吗？** 主控制完好时，纵深防御层的缺失是加固建议，不是漏洞 → FP（或按 hardening 处理）；主控制本身缺失或可绕过 → TP，且严重度按实际击穿的边界评。反向陷阱也在这条里：别把"有纵深防御"当成主控制存在的证据——去主控制上验证。

## 拒绝合理化表

triage 时如果冒出下面这些念头，停下来——它们都是绕过核对纪律的借口。

| 借口 | 为什么不成立 | 必须动作 |
|---|---|---|
| "看起来像误报" | 直觉不是证据，复核结论必须可指认、可复查 | 指认模式类别 + 引用证据行号 |
| "可能是误报，先放行" | 不确定不是放行理由——三态里就是为它准备了 needs_validation | 判 needs_validation 并写明缺失的具体事实 |
| "规则报了应该有" | 规则是模式匹配，模式 ≠ 漏洞，双向都成立 | 完成从入口到 sink 的数据流 trace 再下 verdict |
| "框架应该会处理" | "应该"是猜测；框架防护必须有实际调用点才作数 | 找到防护调用的具体行，找不到就不算 |
| "测试文件里的问题不重要" | 测试里的真实凭证照样是泄露；模式噪音和真实暴露要分开判 | 按模式 1 的两个例外逐条排查 |
| "这个严重度感觉该更高" | 严重度不能超过已证明的影响；"感觉"不进 severity | 按报告的严重度锚点重写影响陈述，写不出具体损害就降级 |

## 魔鬼代言人复核（true_positive 放行闸门）

在给出任何 `true_positive` 前，用一句话构造**最强的反方论证**："这个发现为什么可能是误报"——对照上面 10 类模式逐类快筛，找出最像的那一类，尝试用源码证据把它坐实。

- 反方论证失败（找不到可坐实的模式类别）→ 放行 `true_positive`，reasoning 里写明排除了哪类、证据是什么。
- 反方论证成立 → 改判 `false_positive`（证据充分时）或 `needs_validation`（还差一个源码外的事实时）。

复核结果写进该条目的 reasoning——没有记录的复核等于没做。
